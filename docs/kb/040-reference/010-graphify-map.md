# Graphify Map

Regenerated on `2026-10-19` with `pnpm run kb:graph` on top of `d2cf268`
(release 1.9.0 in progress, the Phase 17 port's 22a–22e and 22g in): 5,253
nodes, 13,035 edges, and about 267 communities (the clustering moves by a few
between runs). Of those, 670 nodes are the knowledge base's files and
headings, and 1,448 edges are its own (`_origin: "kb"`, below): 124
`contains` and 1,324 `mentions`. Refresh after code or knowledge-base changes with
`pnpm run kb:graph`; if a query looks stale, compare `built_at_commit` against
`git rev-parse HEAD` and inspect the working tree.

Artifacts in this repository:

- `graphify-out/graph.json`: the graph of code and knowledge base (tracked).
- `graphify-out/GRAPH_REPORT.md`: generated graph report (tracked).
- `graphify-out/GRAPH_TREE.html`: HTML tree view, regenerated by `graphify tree`
  (tracked).
- `graphify-out/graph.html`: the interactive view, a vis.js network with a
  search box, a community filter and a panel that shows a clicked node's
  connections, nodes sized by degree. `kb:graph` rewrites it last, so it
  shows the knowledge base too; open it with
  `xdg-open graphify-out/graph.html`. It loads `vis-network` from
  `unpkg.com`, so it needs a network connection. Above 5,000 nodes (or
  `GRAPHIFY_VIZ_NODE_LIMIT`) graphify skips it. The graph passed that on
  `2026-10-19` (5,253 nodes), so `kb:graph` now sets
  `GRAPHIFY_VIZ_NODE_LIMIT=8000` for its `cluster-only` step. It is tracked
  (about 5.7 MB) at the maintainer's choice; the `.gitignore` line that
  ignored it was removed.
- `graphify-out/manifest.json`: the per-file extraction cache keyed by mtime,
  ignored alongside `.graphify_*` and `cache/`.
- `graphify-out/<date>/`: the dated backup graphify takes before a rewrite,
  ignored.

Scope and limitations:

- No semantic (LLM) extraction runs, because no API key is configured, so
  token cost is `0 input / 0 output`. Code is extracted from its AST (symbols,
  imports, calls), and Markdown by graphify's structural scan: each file and
  heading is a node, and a link to another `.md` file is a `references` edge.
  Communities are named after their hub node; `graphify label` would need an
  LLM.
- It is good for architecture and navigation over symbols, imports, calls and
  structure, and for finding the knowledge-base sections about a piece of
  code. It is not evidence of product semantics in README, docs or images.

**How the knowledge base sits in the graph.** graphify sees each section file
and the index's link to it, but not the knowledge base's tree, and not the
code a section talks about, since it ignores links to anything but documents.
`node docs/kb/housekeeping.mjs --graph` (the second step of `kb:graph`, code in
`docs/kb/graphify.mjs`) adds both:

- `contains` edges from the index to each group, from a group to its
  sections, and from a section to its subsections;
- `mentions` edges from a section to the code it names in inline backticks
  outside fenced blocks. A path that matches exactly one file is `EXTRACTED`.
  A code-shaped name (camelCase, PascalCase or snake_case, four characters or
  more, with any `.`/`::` qualifier and `()` dropped) that matches one to
  three symbols is `INFERRED`, since a name can match the wrong symbol. Plain
  words, ambiguous paths and names shared by more symbols get no edge.

These edges carry `_origin: "kb"` and the section file as `source_file`, the
provenance graphify gives its own non-AST edges, so a later `graphify update`
(by hand or from a git hook) keeps them while both ends exist and drops them
with their section file. It does not add new ones, so run `kb:graph` again
after changing the knowledge base. Each run removes every `kb` edge before
adding the current set, and it rewrites `graph.json` only after checking that
it reproduces graphify's own formatting byte for byte, so it changes nothing
else in the file. It fails, changing nothing, if a section file is newer than
the graph; `kb:graph` runs `graphify update .` first for that reason.

`pnpm run kb:graph` runs, in order: `graphify update .`, the step above,
`graphify cluster-only .` (so communities account for the new edges, and the
knowledge-base records cluster with the code they describe; it also rewrites
`graph.html` and `GRAPH_REPORT.md`), and `graphify tree`.

Useful graph commands:

```bash
graphify query "loadCommits requestLoadCommits GitGraphView" \
  --graph graphify-out/graph.json

graphify explain "readCommitDetails()"   # its code neighbors, and the sections that mention it

graphify explain "280-diff-parity-against-real-history-and-a-gix-myers-fix.md"

graphify path "src/webview/main.ts" "src/backend/queries/loadCommits.ts" \
  --graph graphify-out/graph.json
```

Query tip: the graph is structural, so symbol names work better than broad
natural-language product questions. For example, `graphify explain
"loadCommits"` resolves the backend query at
`src/backend/queries/loadCommits.ts` and shows its imports and calls, and
`graphify query "readCommitDetails DiffDocProvider"` also returns the
knowledge-base records about commit details and diffs.
