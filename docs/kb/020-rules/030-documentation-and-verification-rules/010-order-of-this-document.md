# Order of this document

This knowledge base is ordered by importance, so a reader who stops early has
still read what matters most. Its index, `docs/kb/README.md`, comes first.
The groups follow it in this order; each one is a file in `docs/kb/` with a
directory of the same name holding its sections:

1. **Mission** (`010-mission`).
2. **Rules** (`020-rules`): the note on reading this knowledge base,
   maintainer and agent policy, commit signing, and these documentation and
   verification rules.
3. **Licensing** (`030-licensing`): license verdicts and clean-room records.
4. **Reference** (`040-reference`): the graphify map, architecture, UI rules,
   telemetry, and other standing guidance.
5. **Ongoing work** (`050-ongoing-work`): the work order and the active
   roadmap phase.
6. **Future work** (`060-future-work`): roadmap phases with open items, and
   recorded directions nobody has started.
7. **History** (`070-history`): completed phases and dated records of
   finished work, oldest first. Older notes call earlier records "above",
   and this order keeps them right.

**Layout.** Every section is one file named `<NNN>-<slug>.md`: a three-digit
prefix that orders it among its siblings, then its title in lowercase words.
A section with subsections has a directory of the same name beside it, where
they follow the same rules. Number new siblings in steps of ten so one can
later go between two without renaming either. A section file starts with
front matter, then its one `# Title`:

```markdown
---
summary: >-
  What the index says about this section, wrapped over as many indented
  lines as needed.
always_read: true
---

# Title
```

`summary` is required and always a folded block (`>-`), which needs no
quoting whatever the text says. `always_read: true` is optional; it puts the
section on the index's *always read* list and marks its entry. Headings inside
a section (`##` and below) are its own structure and stay out of the index; if
a part deserves an entry, it becomes a section of its own.

**The index is generated.** `docs/kb/housekeeping.mjs` builds the list in
`README.md` between `<!-- kb-index:start -->` and `<!-- kb-index:end -->` from
the files themselves: groups and sections in prefix order, subsections
indented under their section, each linked by path with its summary, the
*always read* ones flagged and also listed on their own at the top. The text
above the markers is written by hand and kept.

- `pnpm run kb:index` rewrites the list. Run it after adding, removing,
  renaming, or moving a section, or changing a title or front matter.
- `pnpm run kb:check` changes nothing and fails when the list is stale, or
  when a file breaks the layout above: a bad name, a reused prefix, a
  directory without its section file, missing or unsupported front matter,
  or a file with no `# Title` or more than one. The test suite runs it on
  this knowledge base, so a stale list fails `pnpm run test`.
- `pnpm run kb:graph` puts the knowledge base into the graphify graph: its
  tree, and which code each section mentions. Run it after changing the
  knowledge base or the code; see Graphify Map under Reference.

To keep it in that order:

- Put a new section in the group it belongs to. A new dated record of
  finished work is a new file at the end of History, with the next prefix.
- When work finishes, move its file (and its directory, if it has one) from
  Ongoing work or Future work to History with `git mv` in the same change
  that marks it done, and update the status table in Implementation Roadmap.
- When a dated record produces a standing rule, put the rule in Rules,
  Licensing or Reference, and have the record point to it rather than
  repeat it.
- Refer to another section by its title; its path is in the index.
- Run `pnpm run kb:index` in the same change.

Until `2026-10-18` all of this was one file, `docs/AI_DEV_KNOWLEDGE_BASE.md`,
whose hand-kept Contents listed each section with its line number. It was
split because agents read it through line offsets that every edit above a
heading moved: at ~125,000 tokens it was several times what one read
returns, while its sections run to 49 lines at the median and 528 at most.
The split moved every line verbatim and kept every Contents summary and
*always read* mark; `git log --follow` on a section file stops at the split,
so look up older history on the old path.
